## Findings

### F1 — [stage-2] Switching to another app makes the controls forget the focused control, so a phase end drops focus to `<body>` — **Fix now**

- **Where:**
  - `src/renderer/src/screens/TimerScreen.tsx:145-155`, the condition at `:151`.
  - The layout effect it starves: `TimerScreen.tsx:79-84`.
  - AC: n/a (accessibility, an N5 regression from T32). The case is the usual one because AC-06
    says the app never raises its window.
- **Problem:**
  - When the window deactivates, Chromium fires `blur`/`focusout` on the focused control with
    `relatedTarget === null`. The control is still connected and still `document.activeElement`.
  - The T32 `onBlur` microtask can't tell this from a click on the background, so it clears
    `lastFocusedControl`.
  - Scenario: the user tabs to Reset during a focus session and switches to another app. The phase
    ends while they are away and Reset unmounts. The ref is already cleared, so focus falls to
    `<body>`, and when they come back the next Tab starts from the top.
- **How it was reproduced:**
  - In the built app, with Playwright focus emulation turned off over CDP
    (`Emulation.setFocusEmulationEnabled { enabled: false }`). With emulation on,
    `document.hasFocus()` stays true, which is why no e2e test sees the case.
  - At HEAD, `activeElement` is BODY after the phase end. A build with the T32 clearing removed
    moves focus to Start.
  - The `contains(relatedTarget)` variant suggested in review-2026-11-08 P3 has the same hole.
- **Resolution:**
  - Forget the control only when focus has really moved off it: add
    `document.activeElement !== left` to the condition at `:151`.
  - The reviewer patched this into a scratch build. P3 (background click, then phase end) keeps
    `<body>`. N5 (Enter on Reset) moves focus to Start. The window-blur case moves focus to Start.
  - Add a component test: `reset.focus()`, `fireEvent.focusOut(reset)`, flush the microtask,
    re-render without Reset, and expect Start to have focus. The test fails at HEAD and passes
    with the patch.
  - Also correct the comment at `:146-148`. Under React 19 the blur-on-removal is not delivered
    during commit, so the comment overstates why the microtask is needed.

### F2 — [stage-2, low] No test checks that the held-key guard survives a caller's `onKeyDown` — **Fix now**

- **Where:** `src/renderer/src/components/ui/Button.test.tsx:20-25`; `Button.tsx:28-34`.
  AC-02, AC-12 (the guard they rely on).
- **Problem:**
  - The merge in `Button.tsx` is correct today.
  - But a mutation where the caller's `onKeyDown` replaces the guard
    (`{...(onKeyDown ? { onKeyDown } : {})}` after `{...props}`) passes all 75 renderer tests.
  - No caller passes `onKeyDown` yet, so the first caller that does would silently lose the
    guard.
- **Resolution:** in the "still calls the caller's onKeyDown" test, also assert
  `expect(fireEvent.keyDown(button, { key: 'Enter', repeat: true })).toBe(false)`.
