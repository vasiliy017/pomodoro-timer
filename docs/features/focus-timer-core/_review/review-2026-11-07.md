## Findings

### N1 — [stage-1] Holding Enter on the primary button toggles Start, Pause and Resume over and over — **Fix now**

- **Where:** `src/renderer/src/screens/TimerScreen.tsx:57-61` (`onSingleClick` checks only
  `event.detail`) with `:131` (`key={primary ? 'primary' : name}`). AC-02.
- **Problem:**
  - The R10 fix keeps focus on the same primary button, so keyboard auto-repeat reaches it again.
  - Each repeated Enter keydown fires a click with `detail 0`, which the R1 guard lets through.
    Each click is sent at the newly broadcast revision, so it applies.
  - The reviewer reproduced this against the built app: focus Start, hold Enter (one keydown and
    4 repeats). The revision went 0 → 5 (Start, Pause, Resume, Pause, Resume).
  - The previous review assumed a stable button would not bring back the double toggle. For
    keyboard users it does.
- **Resolution:**
  - Ignore repeated Enter/Space keydowns on the control buttons (`event.repeat` →
    `preventDefault`), next to `onSingleClick`.
  - Add an e2e-through-UI test that holds Enter on Start and asserts the revision goes up by
    exactly 1.
  - Add a component test that asserts the `preventDefault`. jsdom doesn't turn key presses into
    clicks, so it can't do more.

### N2 — [stage-1] Two of the four steps in the e2e double-click test pass with or without the R1 fix — **Fix now**

- **Where:** `e2e/timer.spec.ts:233-238`, `:135-145`; `TimerScreen.test.tsx:56`. AC-02,
  `test-plan.md:47`.
- **Problem:**
  - Measured in the built 420×560 window:
    - Start's centre misses both the running Pause button and Restart cycle, so the second press
      of the Start double-click lands on empty space.
    - Skip's centre misses every button on the ready short break, so the second Skip press lands
      on nothing too.
  - Only Pause and Resume share a position, so only those two steps would fail without the guard.
  - So AC-02's example ("a second Skip … does not also skip the break that is now ready") has no
    test through the UI.
  - The component test covers `detail 2` only for Start and Restart cycle.
- **Resolution:**
  - After the first press, assert that `document.elementFromPoint(x, y)` is a control button, so
    a step cannot silently miss.
  - Drive the Skip case where a control does replace the old one under the pointer.
  - Widen the component `it.each` to all five controls.

### N3 — [stage-1] The contract and the SAD still say an ignored command changes nothing — **Fix now**

- **Where:**
  - `docs/features/focus-timer-core/contracts/public-api.md:119` ("`ignored` never changes state")
  - `sad.md:375` and `:480` ("The revision is stale, so nothing changes")
  - `src/shared/timer.ts:241` ("Commands have none")
  - AC-02, AC-05, AC-07.
- **Problem:**
  - Since R2 (`timer.ts:283-288`), a command that reaches a running phase already past its end
    does three things:
    - it ends that phase, with the revision bumped and a new notice;
    - it returns `notify` and `bounceDock`;
    - it still comes back as `ignored`/`staleRevision`, carrying a newer snapshot.
  - The behaviour is right, but the Accepted contract and SAD Flow 4/6 contradict it, and no ADR
    records the rule.
  - The new-day reset before a command already broke the same invariant quietly. The property
    test excuses both cases.
- **Resolution:**
  - Amend `public-api.md` §1 (invariants) and §2 (return table): an ignored command can still
    settle a phase that is already due, or start the new day, first.
  - Add an `alt` branch to `sad.md` Flow 4: the phase was already due, so it ends first, with its
    signals, and the command is stale.
  - Fix the comment at `timer.ts:241`.

### N4 — [stage-1] The cold-launch e2e test failed the 2 s budget once — **Fix now (measure inside the app)**

- **Where:** `e2e/boot.spec.ts:30`. Spec §6 (launch ≤ 2 s).
- **Problem:**
  - The first `npm run test:e2e` run straight after the build failed "cold launch 1" at 2409 ms.
    Reruns took 1.0–1.4 s.
  - The clock runs from before `electron.launch` until the heading is visible, so it includes
    Playwright's attach overhead.
  - With three launches (R8), that one slow first launch can fail CI.
- **Resolution:** measure inside the app, from main's process start (for example
  `performance.timeOrigin`) to the first rendered snapshot, and keep the 2 s budget.

### N5 — [stage-2] Keyboard focus is still lost when Reset or Skip removes itself — **Fix now**

- **Where:** `src/renderer/src/screens/TimerScreen.tsx:131`; control table `src/shared/timer.ts:137-138`.
  AC: n/a (accessibility, the remainder of R10).
- **Problem:**
  - Only the primary slot has a stable key. Reset and Skip are still keyed by name.
  - **Scenario 1:** Reset on a running focus session makes the phase ready. Reset unmounts and
    focus drops to `<body>`.
  - **Scenario 2:** Skip on a ready short break leads to a ready focus session, which has no
    Skip. Focus drops the same way.
  - In both cases the next Tab starts from the top of the document.
- **Resolution:**
  - After a snapshot change, if the focused control is gone, move focus to the primary button
    through a ref.
  - Add component tests for Reset and Skip next to the R10 test.

### N6 — [stage-2] The second-launch e2e helper can hang and leave Electron running — **Fix now**

- **Where:** `e2e/timer.spec.ts:86-91`. AC-13 / AC-03 tests.
- **Problem:**
  - `launchSecondInstance` resolves only on `exit`, with no timeout and no kill.
  - If a regression breaks the single-instance handover, the spawned app opens its own window and
    never exits.
  - Playwright then times out with a vague error, and an orphaned Electron process with a visible
    window outlives the run.
- **Resolution:** race the exit against a timeout of about 10 s that calls `child.kill()` and
  rejects with "second instance did not quit".

### N7 — [stage-2] The relaunch e2e leaks the first app on failure and has one assertion that cannot fail — **Fix now**

- **Where:** `e2e/timer.spec.ts:368-379`. AC-13.
- **Problem:**
  - `before.close()` (`:373`) runs only on the happy path. If an assertion fails before it, the
    app is never closed and its `userData` is deleted under it.
  - `getByText('of 4 completed')).toBeHidden()` (`:379`) can't fail: the cycle line renders only
    on breaks, and the relaunch shows a focus phase.
- **Resolution:**
  - Wrap `before` in its own try/finally.
  - Replace the assertion with a `timerGetState()` check that `completedInCycle === 0` and
    `revision === 0`.
