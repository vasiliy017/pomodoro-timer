## Findings

### P1 — [stage-1] Holding Enter on Restart cycle opens the confirmation dialog, then a key repeat closes it — **Fix now**

- **Where:**
  - `src/renderer/src/components/ui/Dialog.tsx:41`: Cancel gets focus as soon as the dialog opens.
  - `Dialog.tsx:73`, `:76`: the dialog's buttons have no held-key guard.
  - `src/renderer/src/screens/TimerScreen.tsx:74-76`, `:176`: the guard covers only the timer
    controls.
  - AC-02 (`spec.md:145` names Restart cycle), AC-12.
- **Problem:**
  - The first Enter on Restart cycle gets `needsConfirmation`, so the dialog opens and focus
    moves to Cancel.
  - The next auto-repeated keydown lands on Cancel, which has no guard, so it clicks Cancel and
    the dialog closes.
  - Both reviewers reproduced this in the built app. With 1 keydown and 4–6 repeats, the
    dialog opened once and closed once, and the revision did not change.
  - Nothing is lost, because Cancel takes focus before Confirm. But a held press does not have
    the effect of one press, which AC-02 requires.
  - Found by both reviewers. The stage-2 pass filed it as stage-2; it is merged here as stage-1
    because AC-02 names the control.
- **Resolution:**
  - Move the held-key guard (`dropHeldKeys`) into the `Button` primitive, so every button in the
    app, the dialog's included, ignores Enter/Space auto-repeat.
  - Add a component test that opens the dialog, fires a `repeat: true` Enter on Cancel, and
    asserts the dialog stays open.

### P2 — [stage-1] The launch-time test starts its clock at Node's start in main, not at process start — **Fix now (`performance.timeOrigin`)**

- **Where:** `e2e/boot.spec.ts:38-40`; `test-plan.md:173`. Spec §6 (launch ≤ 2 s).
- **Problem:**
  - `Date.now() - process.uptime() * 1000` gives the moment Node initialised inside Electron's
    main process. Chromium/Electron startup before that point is not counted.
  - In probes outside the repo, this origin was 95–273 ms after a bare spawn and 548–627 ms
    after the spawn under `electron.launch`. Main's `performance.timeOrigin` was 25–85 ms after
    the spawn.
  - The comment ("from main's process start") is therefore inaccurate, and cold launch is
    under-reported.
  - The budget is still met: in-app figures were 875–1101 ms, and spawn to heading paint was
    1452–1728 ms.
- **Resolution:**
  - Start the clock at main's `performance.timeOrigin`, the real process start, and keep the
    2 s budget.
  - Correct the comment to match.

### P3 — [stage-2] A stale remembered control pulls focus from `<body>` to the primary button — **Fix now**

- **Where:**
  - `src/renderer/src/screens/TimerScreen.tsx:90`, `:94-99`, `:157-159`.
  - Test gap: `TimerScreen.test.tsx:105-112`.
  - AC: n/a (accessibility, the remainder of N5).
- **Problem:**
  - `lastFocusedControl` is set on focus and never cleared when focus leaves the controls. The
    effect can't tell "the focused control was just removed" apart from "focus was already on
    `<body>`".
  - Reproduced in the built app: focus Reset, click the window background, then let the focus
    session end, which removes Reset. Focus jumps to Start, so a stray Enter or Space starts the
    break.
  - The "leaves focus alone" test never reaches this path, because the ref is still `null`
    there. It would also pass if the `activeElement === body` check were deleted.
- **Resolution:**
  - Clear the ref when focus leaves the controls for a reason other than removal. For example,
    use an `onBlur` on the controls container that clears it when
    `event.target.isConnected && !event.currentTarget.contains(event.relatedTarget)`.
  - Add a component test: focus Reset, `blur()`, re-render with Reset gone, and expect `<body>`
    to keep focus.
